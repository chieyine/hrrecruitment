# FRAD Recruitment Platform — code, product and design audit

Audit date: 28 July 2026

## Outcome

This pass treated the repository as a recruitment product, not a collection of
screens. The application now has a coherent FRAD visual language, role-aware
navigation, clearer candidate and staff journeys, faster high-traffic queries,
more reliable scheduled work, and copy written for real recruitment operations.

The companion [COMPLETE_FILE_AUDIT.md](./COMPLETE_FILE_AUDIT.md) is the
machine-generated first-party file ledger. Each row records the exact path,
layer, size, content hash and applicable verification. It is deliberately an
inventory, not a false claim that a hash proves code quality.

## Material defects found and corrected

### Scheduled work could exhaust its entire execution budget

When SMTP was configured but unreachable, the outbox processed messages
sequentially and each connection could remain open for about a minute. That made
the schedule processor appear hung and could prevent later jobs from running.

Correction:

- explicit connection, greeting and socket timeouts with safe defaults;
- bounded outbox batches;
- controlled message concurrency while preserving leases, retries and
  dead-letter handling;
- documented environment controls in the example configuration.

### Recruitment dashboards performed avoidable serial work

Independent staff-dashboard queries were awaited one after another. The command
centre now executes independent reads in parallel and presents the live
pipeline, attention queue, movement and new-starter readiness as one operational
view.

### The vacancy register loaded application records it did not use

Vacancy rows fetched entire application collections only to display a count.
The query now uses Prisma relation counts, reducing transferred data and object
construction as vacancy/application volume grows.

### Candidate complaints could silently turn a failed request into an empty state

The complaints screen now checks response status, reports actionable failures
and cancels stale requests. A network or server error is no longer presented as
“no complaints”.

### Navigation and product identity were fragmented

The global shell now distinguishes public, candidate and staff contexts. It
exposes the full recruitment product without crowding the primary navigation,
shows account context, supports mobile navigation, and uses accurate footer
labels for candidate and recruitment-administration destinations.

### The audit generator overstated repository scope

Generated build output, storage, coverage and Playwright artefacts could enter
the file ledger and inflate the result by thousands of files. The generator now
records only first-party repository material and labels database migrations
correctly.

### Browser tests depended on execution order and stale interface text

The application-draft flow now creates its own candidate, selectors match the
real accessible controls, route coverage has an appropriate explicit budget,
and the E2E configuration retains isolated-database safeguards.

## Product and design work

The redesign establishes a restrained FRAD system rather than a generic
dashboard theme:

- warm paper surfaces, deep institutional green and a measured copper accent;
- serif display type paired with a legible system sans;
- stronger hierarchy, spacing, density, focus states and restrained motion;
- consistent controls, tables, cards, status marks, skeletons, dialogs,
  pagination and notifications;
- editorial public careers pages rather than a template hero-and-card layout;
- a staff command centre built around decisions and operational attention;
- a calm candidate overview centred on profile readiness, active applications
  and next actions;
- responsive layouts verified at desktop and mobile widths;
- print behaviour and reduced-motion support retained in the global system.

Copy was rewritten around the language a candidate or recruitment team actually
uses. A final scan found no user-facing instances of the targeted stock phrases
such as “seamless”, “empower”, “leverage”, “unlock”, “revolutionise” or
“journey”.

## Remaining technical debt

ESLint reports 28 non-blocking warnings. Twenty-seven are React Compiler
advisories for state updates initiated by effects (primarily initial client-side
data loading or local-storage hydration); one is the anonymous default export in
the ESLint configuration. These are not current build, test or runtime failures,
but converting the relevant pages to server-loaded data or dedicated client
query hooks would reduce cascading renders and make them more compiler-friendly.

The application should still be exercised with production identity, mail,
object-storage, monitoring and ERP credentials in a staging environment before
deployment. The local review used isolated test services and did not contact
production systems.
